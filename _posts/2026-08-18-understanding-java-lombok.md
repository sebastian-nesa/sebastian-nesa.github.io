Lombok is a Java library that helps reduce boilerplate code, by generating getters, setters, constructors and helper methods (`equals()`, `hashScode()`, `toString()`) at compile time through the use of annotations.

How it works:

1. **Using Annotations**: The developer annotates a class which specify the type of boilerplate code to generate. 
2. **Compilation Phase**: The compiler reads the annotations and Lombok's annotation processor intercepts the compilation process. It identifies them and their respective elements classes, attributes or method.
3. **Code Generation**: Lombok generates bytecode based on annotations and their fields. These include methods such as getters and setters, helper methods as well as constructors.
4. **Merging**: The bytecode generated by Lombok is then merged with the original source code by the compiler. 
5. **Bytecode Generation**: After merging, the compiler produces bytecode ready to be executed by the JVM.

Lombok therefore helps developers focus their attention on business logic and reduce errors rather than spending time on mundane tasks.

## An Example

Consider the following class:

```java
class Employee {
    private String name;

    protected Employee() {}
    protected Employee(String name) {
        this.name = name;
    } 

    public String getFirstName() { return firstName; }
    public void setLastName(String lastName) { this.lastName = lastName; }
}
```

Using Lombok annotations much of the boilerplate can be eliminated:

```java
@Getter
@Setter
@NoArgsConstructor
@RequiredArgsConstructor
class Employee {
    private String name;
}
```

To further reduce boilerplate, annotations `@Getter`, `@Setter` and `@RequiredArgsConstructor` can be replaced by the `@Data` annotation. The `@Data` annotation also provides implementations to helper methods: `equals()`, `hashScode()`, `toString()`. The above snippet can be rewritten as:

```java
@Data
@NoArgsConstructor
class Employee {
    private String name;
}
```

## Pros of using Lombok

- **Reducing Boilerplate Code**: Lombok helps with reducing boilerplate code for Java classes of all sizes through the use of annotations such as `@Getter`, `@Setter`, `@Data`, `@Value`. 
- **Support for Immutable Classes**: `@Data` creates mutable classes, while `@Value` offers immutable support
- **Cleaner Code**: Using Lombok reduces the number of lines of code which helps making it more readable and easier to understand. 
- **Builder Pattern**: the `@Builder` annotation helps implement a builder pattern for a class. Useful for creating a fluent APIs.
- **DTOs(Data Transfer Objects)**: Lombok can help with creating DTOs with less code.

## Common Annotations

- `@Getter` generates getter methods
- `@Setter` setter methods
- `@ToString` generates a standard toString() implementation displaying the class name and fields
- `@EqualsAndHashCode`: Generates `equals(Object)` and `hashCode()` implementations checking all non-static, non-transient fields.
- `@RequiredArgsConstructor`: Generates a constructor for all final fields and any fields marked with `@NonNull`
- `@Data` provides mutable classes 
- `@Value` immutable classes

## Examples for `@Data` and `@Value`

```java
import lombok.Data;
import lombok.NonNull;

@Data
public class Employee {
    private final Long id;          // Included in constructor, getter only
    @NonNull private String email;  // Included in constructor, getter, and setter
    private String name;            // Getter and setter (not in constructor)
    private int age;                // Getter and setter (not in constructor)
}
```

`@Value` provides immutability and it:

- **Makes the class final**: Prevents other classes from extending it.
- **Makes all fields final and private**: Ensures fields cannot be reassigned or accessed directly after object creation.
- **Generates `@Getter`**: Creates public getter methods for all fields.
- **Generates `@AllArgsConstructor`**: Creates a constructor containing every single field in the class.
- **Generates `@ToString` and `@EqualsAndHashCode`**: Standard implementations that evaluate all fields.
- **No Setters**: Completely omits `@Setter` annotations so field values cannot be modified

Concretely:

```java
import lombok.Value;

@Value
public class Employee {
    public String name;
    public int age;
}
```

Lombok modifies the class to:

```java
public final class Employee {
    private final String name;
    private final int age;

    public Employee(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() {...}
    public int getAge() {...}


    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
    @Override public String toString() { ... }
}
```
## JPA Pitfalls

Never apply `@Data`, `@ToString` or `@EqualsAndHashCode` annotations to a JPA `@Entity` as these macros execute reflection across all class properties. If the entity contains a lazy-loaded relational mapping (e.g. `@OneToMany`), evaluating `toString()` or `hashCode()` triggers unintended database query, yielding a `LazyInitializationException` or O(N) performance degradation.

Let's look at an example of a service method in Spring Boot (assume `EmployeeEntity` has been annotated with `@ToString` and that it also has a many to one relationship with another entity `Project` (an employee can work on multiple projects)):

```java
@Transactional
public EmployeeResponseDTO createEmployee(EmployeeRequestDTO request) {
    if (employeeRepository.findByPersonalNumber(request.personalNumber()).isPresent()) {
        throw new IllegalArgumentException("Personal number already exists: " + request.personalNumber());
    }

    EmployeeEntity entity = employeeMapper.toEntity(request);
    EmployeeEntity savedEntity = employeeRepository.save(entity);
    return employeeMapper.toDTO(savedEntity);
}
```

EmployeeEntity entity can be in four states:

1. **Transient**: instantiated in memory (after being assigned to by `employeeMapper`). It has no association with the database or Hibernate Session.
2. **Managed**: associated with an active Hibernate Session. Changed to the entity are tracked and automatically synced with the database (dirty checking). Occurs after `employeeRepository.save()`. Note that here after the employee is saved to the database it has no Project entries assigned to himself.
3. **Detached**: the object exists in memory, but the Hibernate Session that loaded it has been closed.
4. **Removed**: scheduled for deletion.

There are two cases:

1. Entity is in transient state:

```java
EmployeeEntity entity = employeeMapper.toEntity(request);
    System.out.println(entity);
```

At this point `projects` has not been queried and has the value of null (or an empty array list). The evaluation of `toString()` for projects evaluates to the string "null". No database query is executed because the entity is transient.

2. Entity is in managed state:

```java
EmployeeEntity entity = employeeMapper.toEntity(request);
    EmployeeEntity savedEntity = employeeRepository.save(entity);
    System.out.println(savedEntity);
```

Step-by-step execution:

1. `save()` executes and returns an entity 
2. By JPA specification `@OneToMany` relationships are fetched lazily. Hibernate does not query the projects table, instead it injects a dynamic proxy object (e.g. `PersistentBag`) into the entity.projects field.
3. `System.out.println(savedEntity)` invokes the generated `toString()`
4. The Lombok `toString()` methods iterates over all fields. It executes string concatenation: `"EmployeeEntity(id=" + this.id + ", projects=" + this.projects + ")"`.
5. To concatenate `this.projects`, the JVM invokes the proxy's `toString()` method
6. The proxy intercepts the method call. It detects that it has not yet loaded the data
7. The proxy then halts execution and issues a secondary, synchronous call SQL query to the database: `SELECT * FROM projects WHERE employee_id = ?`

Why it fails?

1. Performance Degradation (N+1 Problem): if you log a list of 100 employees, `toString()` will trigger 100 hidden secondary SQL queries, overloading the database
2. Exception: `LazyInitializationException` for example if the `System.out.println(entity)` is executed in the Controller layer after which entity is no longer in a hibernate managed state.

## Conclusion

Lombok can save time but use it with caution when it comes to Entity classes that are managed by hibernate.
